# Ability Themes and Armory Engine Cleanup — Implementation Plan

**Completed 2026-10-30:** Ability themes live in `themes/` (colour roles, `getAbilityTheme`, research trees take `theme:`, two-tone archetype defaults, SVG palette guard). The engine no longer imports Armory content: sentries are `SentryDef`s, weapon art sits on `ConjuredWeaponDef`, weapon effects take parameters, `defineConjure` / `defineThrownWeapon` are archetypes, and `registerArmoryContent()` replaces side-effect imports (called from `AbilityRegistry.ts`, the live hub). `contentLayering.test.ts` guards it, and three Armory AbilityTests cover the sword cycle, turret and shield. Full suite: only the known `earthAttuned.test.ts` failures. Follow-ups: the browser look-over has not been done; the engine still imports `05_earth_core/earthCoreConstants` and `09_gravity_core/gravityConstants`.

Goal: make the Armory's "Quench" palette the first user of a project-wide **ability theme** system, so every ability group (and its research tree, resource, archetypes and art) picks colours by role instead of hex. Then remove the engine's dependency on Armory content: the shared engine code should own generic sentry, dropped-weapon and weapon-effect definitions, and the Armory should register its content with them.

This is a refactor. Gameplay, numbers, fingerprints and checkpoints do not change. The only visible change is that Armory surfaces keep their current colours, now read from a theme.

## Plan-level decisions (locked)

- **No gameplay change.** Every Armory number, timing, RNG draw and serialized field stays the same. `armoryCore.test.ts` and the other tests above must pass with only import-path edits. No `UPGRADE_STEPS` entry. If a step finds it must change a serialized shape, stop and report instead.
- **Theme shape.** `AbilityTheme { id: string; primary: string; secondary?: string; font?: string; shadeFactor?: number }`, CSS hex as the single source. A resolver returns `ResolvedAbilityTheme` with `primary`, `secondary`, `shade`, `font` as both CSS strings and `0x` numbers (`primaryNum`, …). Missing `secondary` falls back to `primary`; missing `shadeFactor` uses `DEFAULT_THEME_SHADE_FACTOR = 0.55` (the Armory's current value); missing `font` stays undefined.
- **Roles (from the Quench decision).** **Primary** = mass: fills, bodies, discs, research border, telegraph fill. **Secondary** = the event: edges, flashes, trails, the resource colour, conjure orbit tint. **Shade** = grips, empty pips, dark detail. **Font** = research card and pill text. These rules are written into `themes/AGENTS.md` and are how new abilities choose colours.
- **Where themes live.** `app/js/games/minion_battles/themes/`: `colorUtils.ts`, `abilityTheme.ts` (types + resolver), `abilityThemes.ts` (the data: one theme per `AbilityGroupId`, plus `weapon`, `generic` and `darkness` themes for trees that are not ability groups). It is a data module like `telegraphStyles.ts`; it imports nothing from `card_defs/`. Content, research trees, resources and archetypes import from it.
- **Lookup.** `getAbilityTheme(abilityId)` reads the group from the first two digits of the id (the existing `AbilityGroupId` convention) and returns that group's resolved theme, or the `generic` theme when the group has none. `getThemeById(id)` serves research trees.
- **Other trees keep their look.** Earth, Light, Gravity, Command, Blood Mage, Darkness, Weapon and Generic get primary-only themes equal to today's `RESEARCH_TREE_COLOUR_*`. Their research chrome and abilities look the same. Recolouring their abilities by role is future work, not this plan; Step 4 only gives archetypes theme defaults that apply when a caller passes no colour.
- **Explicit colours still win.** Archetype and effect inputs keep their colour options. Theme defaults fill only what the caller omits. Existing non-Armory callers that pass colours are untouched.
- **SVG art stays hand-painted** in this plan. A guard test checks that each themed group's SVGs use only that theme's colours plus black, white and `none`/`currentColor`. Placeholder substitution (`{{primary}}`) is out of scope.
- **Engine owns generic definitions; content registers.** Nothing under `game/`, `resources/` or `researchTrees/` imports `card_defs/10_armory_core/` when the plan is done (tests may). A test enforces it (Step 11).
- **Sentry definitions.** `SentryDef { id; shotDamage; shotInterval; shotCount; firstShotDelay; range; coneHalfAngleRad; shotHitRadius; shotSpeed; lifetime; sprite?; deliveryProjectileType?; deliverySpeed?; deliverySpinDegreesPerSecond?; deliveryBodyRadius? }` in `game/fieldObjects/sentryDefs.ts` with `registerSentryDef` / `getSentryDef`. It replaces `registerSentrySprite`. `Sentry` instances keep `defId` and their runtime fields only (def-pattern skill). Turret drawing (`paintTurret`, pose geometry) stays a turret-specific painter for now; only its numbers move next to it.
- **One weapon definition.** `ConjuredWeaponDef` gains `art: { url: string; tipOffsetRad?: number }`, so a weapon's token picture is declared where the weapon is. It keeps `tokenKind`: weapon ids (`armory_sword`, saved as `heldConjuredWeapon.defId`) and token kinds (`sword`, saved as `DroppedWeapon.kind`) are both serialized and differ, so neither is renamed. Art is looked up by token kind through `getConjuredWeaponDefByTokenKind`. The separate `registerWeaponArt` registry is removed.
- **Dropped-weapon flight numbers** (`DROPPED_WEAPON_ARC_*`, `DROPPED_WEAPON_ROTATION_STEPS`) are engine defaults in `game/fieldObjects/landing.ts`. They are the same for every weapon today; do not add per-weapon overrides.
- **Effect and projectile type ids** are owned by the engine file that defines the effect or projectile. Content imports them.
- **Archetypes.** `defineConjure` and `defineThrownWeapon` live in `abilities/archetypes/` next to `defineDirectionalShield`. Create Shield stays on `defineDirectionalShield` with the `startConjureCast` / `equipConjuredWeaponAtEnd` hooks, which move to `abilities/archetypes/conjureCast.ts`.
- **Registration.** `10_armory_core/register.ts` exports `registerArmoryContent()` (conjured weapons + sentry defs), called once from `card_defs/index.ts` next to the other registrations. The ten `import '../armoryWeapons'` lines go away. Tests that build abilities without `card_defs/index.ts` call it (or import the module that calls it) explicitly.
