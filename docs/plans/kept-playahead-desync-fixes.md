# Plan: Kept-Playahead Desync Fixes — Rollback-Only In-Place, Staging Buffer, Divergence Observability

## Context

Follow-up to `docs/plans/non-host-playahead-order-submit.md` (completed 2026-07-07). That work fixed the EC110E order-drop, but live 2-player games (lobbies 0721BF, E2E104, 5E0F6B — all 2026-07-07 evening) still desync. Investigation findings:

**What worked (keep):** the Fix A align-guards passed batch after batch (`hasAcceptedPostAtBatch: true` logged at hostBatch 97/192/290/385/508 in 5E0F6B); Fix B recovery-defer recovered a dropped order via `deferLocalOrder` → flush → accepted POST. No order was permanently lost and no error banner appeared.

**What broke (5E0F6B, the core incident):** at solo-waiter batch 508 the non-host's `wouldCommitInPlace` playahead relaxation allowed an **in-place commit that kept the ITS preview timeline**. The preview's execution of PunchNEW (ability `0120`) diverged from the host's canonical run of the same wire order: the host's unit_2 got its next turn at tick **580** (host paused at batch 580 waiting `[unit_1, unit_2]`), while the client's kept timeline gave unit_2 its next turn at ~**602** — no parallel pause ever formed at 580 on the client (no ITS freeze/drop log between 507 and 601). The host sat waiting for the client at a batch the client doesn't believe exists; all three align-guards were *legitimately* false (nothing deferred/accepted/pending at 580); the soft-align fired as correct recovery and the player experienced a 601→579 rewind. This is the same preview-vs-canon bug family as commits b33da3e ("Fixing double punch") and 36cfe8a ("Fixing digging claws in ITS playahead").

**Key insight:** preview/canon execution equivalence is load-bearing for *any* in-place commit in multiplayer (host in-place commits make the *client* desync symmetrically, since the client replays the wire order canonically). Until that equivalence is verified per-ability, non-host kept-playahead must not launder preview state into the real timeline. The rollback-commit path is canon-safe by construction and still pipelines: the deferred POST flushes when the host catches up, the client then plays forward on canonical orders — this naturally caps the client's lead at ~one batch.

**Secondary bug (0721BF):** `OrderManager.hasPendingOrderForUnit` / `getPendingOrderForUnit` match any row with `gameTick >= atTick`, so a remote order queued for a far-future batch suppresses waiter/pause formation at earlier ticks. Correct for full-replay (pre-queued orders are how replay works — the fetched set through `hostTick` is canon-complete), wrong for rows *beyond* the host's completed tail (a pipelining peer's future rows).

**Debugger patches currently in the working tree (uncommitted) that this plan reworks:**
- A far-future skip in `BattleSession.applyRemoteOrders` gated by `BATTLE_NET_REMOTE_ORDER_MAX_TICK_AHEAD` — right instinct, wrong layer: skipped keys flow back through `skippedKeys` into net-layer `appliedOrderIdHashes` (`OrderQueueController.ts` fetch/replay both register skipped keys) while the fetch cursor advances, so skipped rows vanish until a rescan/bootstrap. This likely *caused* the E2E104 "stuck one tick behind host" symptom.
- A new `maybeAlignWhenBehindHostPausePlane` soft-align patching that E2E104 symptom — unnecessary once staging replaces the skip.
- `submitCommittedTargetingOrder` early-returns `false` when `isOrderSubmitPathAvailable()` is false — **this regresses Fix B**: during a recovery window the ITS rollback commit never reaches `submitOrder`'s recovery-defer gate, so the order drops and the "Your order was not accepted" banner returns (the original EC110E bug shape).
- `#region agent log` blocks POSTing to `http://127.0.0.1:7873/ingest/...` left in three production files, plus untracked `.cursor/debug-dcf8d4.log`.

### Design decisions

1. **Non-host in-place-with-playahead → rollback-only (temporary retreat).** Revert the `wouldCommitInPlace` playahead relaxation; keep everything else from the previous plan (guards, accepted-post set, recovery-defer). Re-enabling is a follow-up gated on the Step 5 equivalence tests passing.
2. **Staging buffer for beyond-host rows.** A remote row applies immediately iff `atTick <= latestHeartbeatHostTick` (canon-complete, replay semantics) **or** `atTick <=` the local engine's current `waitingForOrders.atTick` (the client is at that pause and needs it now — the EC110E bootstrap case). Otherwise the row is staged (Map by `idHash`, dedupe keys NOT registered) and re-partitioned on every non-host poll. This replaces both the far-future skip and the one-tick-behind align.
3. **Observability, not new recovery paths.** Fingerprint-compare on every rising `hostTick` during playahead and log match/mismatch in the align warn; add an error-severity "structural divergence" log (pause planes differ while fingerprints at hostTick match). Escalation stays on existing paths.
